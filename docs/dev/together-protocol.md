# Совместный просмотр: протокол

Два телефона смотрят одну серию синхронно, переписываются, шлют реакции и голосовые. Между ними —
релей на Cloudflare, который копирует байты и ничего в них не понимает. Документ описывает всё,
что ходит по проводу, и правила, по которым обе стороны это понимают. Реализации: iOS —
`ios/Together/`, Android — `android/src/main/java/app/kaeru/{domain,data}/together/`, релей —
`infra/relay/`. Правила и числа обязаны совпадать на обеих платформах; где имя константы
различается, оба приведены.

## 1. Роли и комната

Хозяин (`host`) создаёт комнату и держит её. Гость (`guest`) входит по ссылке. Комната живёт в
Durable Object релея под именем `roomId`; в ней ровно два места, третий получает close `4409`.
Отдельного «join» нет — комната определяется путём `wss://<relay>/w/<roomId>`.

Хозяин — эталон времени: подстраивается только гость (§7). Всё остальное симметрично: любой может
ставить паузу, перематывать, менять серию, писать и говорить.

Роль определяется тем, как сторона вошла: `create()` — хозяин, `join(link)` — гость. Хозяин,
получивший собственную ссылку (шторка «Поделиться», переписка с самим собой), её игнорирует —
иначе он перезванивал бы гостем в свою же комнату, и в ней оставались бы два гостя (§10).

## 2. Ссылка-приглашение

```
https://kaeru.vitaliy.velikodniy.name/w/<roomId>#<key>
kaeru://watch?r=<roomId>#<key>          (схема приложения; ключ может лежать и в query как k=)
kaeru://watch?r=<roomId>&h=<ip>&p=<port>#<key>   (LAN-транспорт, устаревший путь)
```

| Часть | Что это | Размер |
| --- | --- | --- |
| `roomId` | 8 случайных байт, base64url без `=` | 11 символов, `[A-Za-z0-9_-]` |
| `key` | ключ AES-128, 16 случайных байт, base64url без `=` | 22 символа |

Ключ живёт во **фрагменте**: браузеры, серверы и релей его не видят, страница `/w/` его не
отправляет ни в один запрос. Цена: некоторые встроенные браузеры мессенджеров теряют фрагмент по
«Открыть в Safari» — страница тогда говорит об этом словами вместо «Установить». На Android ссылка
открывает приложение через App Links или intent-URI со страницы; на iPhone без платной команды
Apple универсальных ссылок нет — страница ведёт в приложение по нажатию на `kaeru://` или
предлагает скопировать ссылку, а приложение читает буфер обмена при выходе на передний план.

Код комнаты (первая половина) безопасно называть вслух; сам по себе он ничего не открывает.

## 3. Транспорт

WebSocket на релей. От телефона к релею — только бинарные кадры (§4), не больше 64 КиБ. От релея
к телефону — только текстовые кадры-команды, и команда одна:

```json
{"type":"peer-left"}
```

Она приходит оставшемуся, когда сокет второго закрылся или оборвался. Правило клиента: бинарный
кадр — данные, текстовый — управление; всё прочее игнорируется.

Коды закрытия от релея (HTTP-статус + 4000):

| Код | Когда | Что показывает сторона |
| --- | --- | --- |
| `4408` | комната шесть часов не видела кадров | «Комната закрылась: в ней шесть часов ничего не происходило» |
| `4409` | в комнате уже двое | «В этой сессии уже двое» (`roomFull`) |
| `4413` | кадр больше 64 КиБ; закрывается отправитель, второй получает `peer-left` | как обрыв |

Все три — «отказы»: после них не перезванивают. Любой другой обрыв — повод перезвонить (§9).

Жизнь сокета: первый дозвон отвечает за себя за 10 с (`dialSeconds`), иначе «Не удалось
подключиться». Дальше read-timeout у сокета **бесконечный** (`socketLifetimeSeconds` = сутки на iOS,
OkHttp без read timeout на Android): комната с одним человеком молчит, и молчание — не ошибка.
Живость проверяется WebSocket-пингом раз в 20 с (`socketPingSeconds` / OkHttp `pingInterval(20 s)`);
пинг без понга за те же 20 с — сокет считается мёртвым, начинается перезвон.

При выходе (`bye`, §8) отправитель ждёт доставки прощания и close-кадра до 1 с
(`goodbyeGraceSeconds` / `GOODBYE_GRACE_MS`) и только потом рвёт сокет.

Релей ограничивает создание комнат: 30 апгрейдов в минуту с одного адреса, дальше `429` с
`Retry-After`.

## 4. Кадр

```
nonce (12 байт) ∥ AES-128-GCM(JSON) ∥ tag (16 байт)
```

- Ключ — из ссылки. Nonce — случайный на каждый кадр, на обеих платформах из системного CSPRNG.
- **AAD** = `roomId` (UTF-8) ∥ один байт стороны отправителя: `0` — хозяин, `1` — гость. Кадр
  открывается только в своей комнате и только под байтом *другой* стороны: отражённый релеем
  собственный кадр не проходит, кадр из соседней комнаты не проходит.
- Кадр, который не открылся под байтом другой стороны, но открылся под своим, — от **второго
  гостя** (§10): единственный отказ, о котором стоит говорить человеку. Прочие нераскрывшиеся
  кадры отбрасываются молча; три подряд (`garbledLimit`/`GARBLED_LIMIT` = 3) — конец сессии.
- Максимум 64 КиБ. Внутри — JSON без пробелов; неизвестные ключи игнорируются обеими сторонами,
  что и позволяет добавлять поля, не ломая установленные сборки.

## 5. Сообщения

Общие поля: `t` — тип, `seq` — счётчик отправителя (§6). Остальное — по типу. Все поля, кроме
перечисленных как обязательные, могут отсутствовать.

| `t` | Обязательные поля | Необязательные | Смысл |
| --- | --- | --- | --- |
| `hello` | `name` (≤ 1024 байт), `animeId` ≥ 0, `episode` ≥ 0, `positionMs`, `playing` | `translationId`, `epoch` > 0 | приветствие и всё состояние отправителя |
| `play` | `positionMs` | | человек нажал play |
| `pause` | `positionMs` | | человек нажал паузу |
| `seek` | `positionMs` | | человек перемотал |
| `episode` | `episode` 1…100 000 | `animeId`, `translationId`, `positionMs` | человек сменил серию или тайтл |
| `state` | `positionMs`, `playing`, `buffering`, `sentAt` | `animeId`, `episode` | отчёт «где я» раз в секунду |
| `chat` | `text` (≤ 4096 байт; экран режет до 200 символов) | | сообщение |
| `reaction` | `kind` ∈ `heart laugh wow sad fire clap` | | реакция |
| `voice` | `chunk`, `total` 1…8, `durationMs` 1…30 000, `bytes` (base64, ≤ 32 768 байт) | | кусок голосового |
| `ping` | `sentAt` | | измерение часов |
| `pong` | `pingSentAt`, `receivedAt`, `sentAt` | | ответ на ping |
| `bye` | — | | человек вышел |

Границы: `positionMs` 0…604 800 000 (неделя), временные метки — миллисекунды Unix
< 10¹⁴, `translationId` ≥ 0. Кадр вне границ — недействителен и отбрасывается.

**Управляющие** сообщения (`play`, `pause`, `seek`, `episode`) участвуют в разрешении конфликтов
(§6); остальные — нет.

### 5.1. `state`: что значат `playing` и `buffering`

`playing` — **намерение**, а не факт: чего хочет зритель (`playWhenReady` на Android,
`rate > 0` на iOS), а не двигается ли картинка. `buffering` — плеер ждёт сеть (загрузка первых
кадров тоже считается). Отсюда четыре состояния:

| `playing` | `buffering` | Что это | Что делает друг |
| --- | --- | --- | --- |
| true | false | играет | подстраивается (гость) |
| true | true | хочет играть, грузится | **ждёт** (§7.3) |
| false | false | пауза | ничего: пауза приходит отдельным `pause` |
| false | true | пауза и грузится | ничего — это просто пауза |

Это различие — вся суть «ждём друга»: пока обе платформы во время заминки сообщали
`playing=false`, ожидание не срабатывало никогда.

`animeId`/`episode` в отчёте — какой серии эта позиция. Отчёт про другую серию не участвует ни в
подстройке, ни в ожидании; отчёт без этих полей (старая сборка) принимается как раньше.

Позиция в отчёте читается с плеера в момент отправки, а не из кэша модели: кэш обновляется
тиком, и отчёт «где картинка была четверть секунды назад» — это друг, устроившийся на секунду в
стороне.

Начало и конец заминки сообщаются **сразу**, вне такта, — иначе ожидание с двух сторон
складывалось бы из двух опозданий по секунде.

### 5.2. `hello`

Несёт всё состояние отправителя: имя, тайтл, серию, озвучку, позицию, играет ли. Отправляется:

- при подключении (и переподключении) любой стороны;
- **повторно раз в 3 с** (`helloRetryMs` / `HELLO_RETRY_MS`), пока собеседник не назвался —
  релей ничего не хранит, и кто вошёл первым, здоровается с пустой комнатой;
- **в ответ на входящее `hello`** — любой стороной, не чаще раза в 3 с (антидребезг), чтобы
  рукопожатие сходилось при любом порядке входа и при потере одного приветствия;
- при прикреплении нового плеера к живой комнате (§8).

`epoch` — случайное число, новое на каждое подключение стороны. Нужно против повтора кадров при
возвращении в комнату (§6). Сборка без `epoch` — прежнее правило.

## 6. Порядок, конфликты, повтор

`seq` — счётчик отправителя, ламповский: получив кадр с `seq` выше своего, сторона поднимает свой
счётчик до него, так что «позже» значит одно и то же на обоих телефонах.

**Replay guard.** Сторона помнит наибольший `seq`, принятый от собеседника, и всё, что не выше,
отбрасывает («out of order»). Релей, который может повторить любой перехваченный кадр, этим
обезврежен — кроме одного случая: возвращение собеседника в комнату, когда его счёт начинается с
единицы. Это разрешено только **`hello` с незнакомой `epoch`**, и только он проходит ниже отметки;
отметка при этом вниз не двигается (следующие кадры вернувшегося по Лампорту всё равно выше того,
что он от нас услышал). `hello` со знакомой эпохой судится по `seq`, как всё остальное. Обе
стороны помнят 32 последних эпохи (`epochsKept` / `EPOCHS_KEPT`). Для сборок без эпохи
действует старое, слабое правило: один `hello` в окне после `peer-left` сбрасывает счёт.

**Конфликт управляющих команд.** Каждая сторона помнит последнюю применённую управляющую команду
(`seq`, чья). Входящая применяется, если её `seq` выше; при равном `seq` **выигрывает хозяин**.
Правило симметрично: гость, читая его со своей стороны, при ничьей проигрывает. `ping`/`pong`/
`state`/чат «победителя» не сдвигают.

Три подряд нераскрывшихся кадра — конец сессии (`garbledLimit`).

## 7. Синхронизация

### 7.1. Часы

Каждые 5 с (`pingMs` / `PING_INTERVAL_MS`) сторона шлёт `ping`; ответ `pong` несёт время приёма
и отправки на той стороне. Из четырёх меток считаются сдвиг часов и RTT; хранится медиана
последних 5 сэмплов (`TogetherClock` / `ClockOffset`, `WINDOW = 5`). Сэмпл отбрасывается, если
RTT > 3 с (`maxRttMs` / `MAX_RTT_MS`: после выхода iPhone из фона накопленные `pong` дают
«RTT», равный времени заморозки) или |сдвиг| > суток (`MAX_OFFSET_MS`).

Позиция друга «сейчас» = `positionMs + (now − sentAt)` (если он играет) + сдвиг часов. Отчёт
старше 5 с (`staleStateMs` / `STALE_STATE_MS`) не используется.

### 7.2. Кто и как подстраивается

**Только гость.** Два телефона, каждый правящий другого по своей оценке часов, устанавливаются на
секунду врозь и перематывают по очереди; хозяин — эталон и не двигается никогда (кроме команд
человека и ожидания, §7.3).

Гость раз в 2 с (`syncMs` / `SYNC_INTERVAL_MS`) смотрит на зазор `gap = |local − remote_now|`,
и только если **оба** играют:

| Зазор | Действие (`decide` / `SyncPolicy.decide`) |
| --- | --- |
| < 200 мс (`convergedMs`) | ничего; идущая коррекция снимается |
| 200…500 мс (`ignoreMs`) | ничего, если коррекция не шла; идущая продолжается до 200 |
| 500…2000 мс (`seekMs`) | скорость 0,97 (впереди) или 1,03 (позади); плеер без управления скоростью — тихий seek при > 1000 мс (`ratelessSeekMs`) |
| 2…10 с | тихий seek |
| > 10 с (`notifyMs`) | seek и «догоняет» на экране |

На iOS для скорости 0,97/1,03 плееру задан `audioTimePitchAlgorithm = .timeDomain`: алгоритм по
умолчанию округляет такие значения до 1,0, и коррекция не работала вовсе.

**Тишина после перемотки.** После собственного seek (коррекционного) 3 с (`correctionQuietMs` /
`CORRECTION_QUIET_MS`) ничего не корректируется, и отчёт друга, по которому прыгнули, забывается:
заминка, которую перемотка сама и вызвала, — не улика. Пока любая из сторон буферизует, коррекций
тоже нет.

### 7.3. Ожидание друга, который грузится

Получив отчёт `playing=true, buffering=true`, сторона ставит паузу, показывает «догоняет» и
ждёт. Отпускает — и играет дальше — по первому отчёту `buffering=false`, либо через 20 с
(`peerLoadingHoldMs` / `PEER_LOADING_HOLD_MS`): дальше ожидание становится замёрзшей картинкой без
объяснения. Два одновременно буферизующих телефона разрывают взаимное ожидание первым же «не
гружусь».

Что с ожиданием делают команды друга: `play` и `pause` его **заканчивают** (пауза друга — пауза;
`play` — играем), `seek` — **переносит**, не заканчивая: друг только что прыгнул и грузит новое
место, ровно поэтому мы и стоим. Снятие ожидания по `seek` без старта картинки оставляло телефон
стоять до нажатия play.

Ожидание — только за того, кто хочет играть (§5.1).

### 7.4. Команды человека

`play`/`pause`/`seek`/`episode` уходят другу только когда их сделал человек. Программные действия
сессии (пауза за друга, старт после ожидания, коррекционный seek, открытие серии по команде) не
уходят обратно — иначе получается эхо: пауза за друга → «друг нажал паузу» → пауза у друга. На iOS
для этого выдержаны окна: 2 с после программной паузы/старта расхождение плеера с намерением не
считается нажатием, 3 с после программного seek/play/pause скачок времени AVPlayer (он переставляет
якорь HLS при возобновлении) не считается перемоткой.

`play`/`pause` от друга применяются с догоном позиции только при зазоре ≥ 500 мс (`catchUpTo` /
`catchUp`): seek на HLS — это заминка, и каждая пауза стоила по одной.

## 8. Серия и тайтл

`episode` несёт `episode` и, с этой версии, `animeId`. Получатель открывает **тот тайтл и ту
серию**; сборка без `animeId` читается как «тот же тайтл». Отчёт друга о прежней серии при этом
забывается (иначе против начала новой он — двадцатиминутный зазор и seek).

Смена серии из меню плеера — `episode`. Открытие **другого тайтла с главной** при живой комнате —
тоже `episode`: новый плеер прикрепляется к комнате и объявляет себя (Android — как локальное
действие `Episode`, iOS — из `attach`, в момент разрешения потока, не дожидаясь первого кадра).
Гость дополнительно **следует за `hello` хозяина** с другим тайтлом/серией — приветствие несёт всё
состояние; хозяин за приветствием гостя не следует.

Озвучка (`translationId`) — пожелание: сторона открывает её, если Kodik у неё такую даёт, иначе
свою, и сообщает об этом на экране.

## 9. Обрыв, возвращение, выход

- **Свой сокет пропал** — перезвон с экспоненциальным backoff примерно на полминуты, буфер
  отправки сохраняется и сливается после дозвона (кадр снимается с буфера только после успешной
  записи, порядок сохраняется). После дозвона — `hello` с новой `epoch` и `ping`. На экране —
  «Восстанавливаем связь…».
- **Друг пропал** — релей шлёт `peer-left`; место держится 30 с (`rejoinWindowMs` /
  `REJOIN_WINDOW_MS`). Вернувшийся здоровается с новой эпохой (§6). Не вернулся — «Связь с другом
  потеряна», сессия завершена.
- **Гость ждёт хозяина** не дольше 30 с (`waitTimeoutMs` / `WAIT_TIMEOUT_MS`) — потом «Не удалось
  подключиться» с «Повторить». Хозяин ждёт гостя сколько угодно.
- **Выход** — `bye`, затем закрытие сокета с ожиданием доставки до 1 с. Друг видит «X вышел» и
  «Сессия закончилась». Отказ от приглашения на экране приглашения (`Не сейчас`) `bye` **не шлёт**
  — гость просто закрывает сокет, хозяин получает `peer-left` и ждёт как обычно; так на обеих
  платформах.
- **Экран приглашения** (гость до «Присоединиться»): все входящие управляющие команды хозяина
  складываются в само приглашение как состояние (последнее актуальное), а плеер, который у гостя
  мог быть открыт на чём-то своём, не трогается — иначе хозяин управлял бы чужим видео.

## 10. Два гостя

Кадр, который не открылся под байтом собеседника, но открылся под собственным, послал другой
гость: ссылку открыли оба, хозяина в комнате нет, и два гостя обмениваются байтами, которых ни один
не может прочитать. Обе платформы показывают «Ссылку открыли оба — комнату держит тот, кто её
создал» и завершают сессию. Хозяин собственную ссылку игнорирует (§1).

## 11. Голосовые

AAC в контейнере MPEG-4 (Apple не декодирует Ogg/Opus, поэтому Android перешёл на AAC), до 30 с,
16 кГц моно — около 3 КБ/с. Клип режется на куски по 32 768 байт (`voiceChunkBytes` /
`MAX_VOICE_CHUNK_BYTES`), не больше 8 (`MAX_VOICE_CHUNKS`), итого ≤ 256 КиБ; каждый кусок — свой
кадр `voice` с `chunk`/`total`/`durationMs`, содержимое в base64url. Сборка на приёме: один клип за
раз, куски строго по порядку, неполный клип забывается через 30 с (`VOICE_TIMEOUT_MS`). Клип,
превысивший лимит, отбрасывается целиком. Пока клип записывается или играет, картинка
приглушается.

## 13. Журнал и проба

Обе платформы пишут журнал сессии — одни и те же строки, без ключей:

- iOS: `Library/Caches/together.log` — `xcrun devicectl device copy from --domain-type
  appDataContainer --domain-identifier app.kaeru.ios --source Library/Caches/together.log`;
- Android: `/sdcard/Android/data/app.kaeru/files/together.log` — `adb pull`, работает и с
  release-сборкой.

Строки: `connect room=… as=host|guest`, `dial ok` / `socket lost …`, `hello out …`,
`frame in <t> seq=…`, `frame refused: …` (не аутентифицировался / не по порядку / другой гость),
`state in pos=… playing=… buffering=… here=…/…`, `holding: the friend is loading` /
`hold released`, `peer left, holding the seat for 30s`, `peer said goodbye`, `failed …`,
`transport closed by this side`, а на iOS ещё шаги открытия серии и смены сцены (`scene
background` — процесс заморожен, кадры придут пачкой).

`tools/together-probe/probe.js` — два клиента протокола на node против живого релея: рукопожатие,
отчёты, ожидание, `peer-left`, ответ релея на close. Запуск: `node tools/together-probe/probe.js`.

## 14. Что не изменить, не сломав установленные сборки

Формат кадра (§4), обязательные поля сообщений (§5), байты сторон в AAD, base64url в ссылке,
имена типов `t`. Новые поля — только необязательные, с поведением «как раньше» при их отсутствии;
так добавлены `epoch`, `state.animeId`/`episode`, `episode.animeId`.
