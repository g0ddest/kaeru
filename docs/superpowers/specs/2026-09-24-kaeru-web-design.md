# Kaeru для браузера — дизайн

Дата: 2026-09-24. Статус: одобрен в разговоре, ждёт ревью текста.

## 1. Зачем

Две задачи сразу, по словам пользователя — «и то и другое»:

1. **Смотреть с компьютера.** Полноценный клиент в браузере: каталог, свой список Shikimori,
   продолжение с места, прогресс, общий с телефоном и телевизором.
2. **Друзья без приложения.** Ссылка «Смотреть вместе», открытая на компьютере, ведёт в веб-клиент
   и сажает в ту же комнату, что телефоны и iPad.

**Доступ только по белому списку** (§6a): веб-версией пользуются лишь аккаунты Shikimori, чьи id
внесены в список; всем остальным — экран входа и «доступ закрыт». Приложения на Android и iOS
этим не затронуты.

Успех первой версии: друг из белого списка на ноутбуке открывает ссылку из мессенджера, входит в
комнату хозяина с Android или iPad и смотрит ту же серию синхронно; владелец аккаунта в том же браузере продолжает
серию, начатую на телефоне, и отметка «просмотрено» появляется на Shikimori.

## 2. Что входит в первую версию

**Входит:**

- Главная: «Продолжить», «Новые серии», «Дальше по списку», «Популярно сейчас», сезон.
- Поиск.
- Карточка тайтла: шапка с артом, факты, озвучка, статус в списке, серии **списком строк** (как на
  iOS после e5bd9d8).
- «Мой список» по вкладкам статусов.
- Вход через Shikimori, отметки серий и статусов пишутся на Shikimori.
- Свой плеер (§5): качество, озвучка, автопереход к следующей серии, пропуск эндинга, клавиатура,
  полный экран, картинка в картинке.
- Совместный просмотр (§7): создать комнату, войти по ссылке, синхронизация, чат, реакции,
  прослушивание голосовых. Запись голосового — только в браузере, который пишет AAC в MPEG-4
  (Safari); в остальных кнопки микрофона нет.
- Firebase Analytics с теми же событиями, что у приложений (§9).

**Не входит:** загрузки и офлайн, Chromecast из браузера, уведомления о новых сериях, вход на
телевизоре по QR, «Обновления», своя светлая тема.

**Позиция внутри серии** («продолжить с 14:20») на Shikimori не хранится. В браузере она живёт в
`localStorage` этого браузера; между устройствами синхронизируется только номер просмотренной
серии — так же, как между телефоном и телевизором сегодня.

## 3. Стек и где живёт

- **TypeScript + React + Vite**, код в `web/` рядом с `android/`, `ios/`, `shared/`.
- Раздаётся **GitHub Pages** с того же домена `kaeru.vitaliy.velikodniy.name`, из той же ветки
  `gh-pages`. Сборка кладёт приложение в корень сайта; файлы скина Chromecast (`kaeru.css`,
  картинки) и `.well-known/` остаются как есть. `404.html` — копия `index.html`, чтобы глубокие
  ссылки (`/anime/1535`, `/w/<комната>`) открывали приложение на статическом хостинге.
- `/w/<комната>#<ключ>` становится маршрутом приложения — экраном приглашения. На телефоне с Kaeru
  эту ссылку по-прежнему перехватывает приложение (App Links / Universal Links) и страница не
  открывается; на компьютере и на телефоне без Kaeru открывается веб-клиент. Кнопки «Открыть в
  Kaeru» и «Установить» с нынешней страницы переезжают на экран приглашения как вторичные.
- **Общий Kotlin-модуль не переиспользуется.** Kotlin/Wasm с Compose даёт тяжёлый бандл, отрисовку
  на canvas, слабые выделение текста, ввод и доступность; клиенту в браузере нужен обычный DOM.
  Логика, которая обязана совпадать с приложениями, закрепляется тестами-векторами (§10).
- Зависимости времени выполнения — только `react`, `react-dom`, маршрутизатор, `hls.js` и Firebase
  JS SDK. Больше никаких сторонних скриптов на странице: токен Shikimori лежит в `localStorage`, и
  любой чужой скрипт мог бы его прочитать.

## 4. Воркер

`infra/relay` — уже релей совместного просмотра и прокси токена Shikimori. Добавляется:

- **`GET /kodik/translations?anime=<shikimoriId>`** — список озвучек тайтла: `get-player` →
  страница плеера → разбор. Кэш каталога на 6 часов в памяти изолята, как `KodikClient`.
- **`GET /kodik/resolve?anime=&translation=&episode=&season=`** — подписанные HLS-ссылки одной
  серии: страница озвучки → `POST /ftor` → расшифровка ссылок. Ответ — список `{quality, url}`.
  Не кэшируется: подпись живёт часы.
- **Токен Kodik** берётся так же, как в `KodikClient`: переменная окружения воркера, иначе токен
  из `kodik-add.com/add-players.min.js`, запомненный на сутки; после отказа — перечитать.
- **CORS** на `/kodik/*` и на `POST /oauth/token` — только для `https://kaeru.vitaliy.velikodniy.name`
  и `http://localhost:5173` (разработка). Остальные маршруты не меняются.
- **Лимит частоты** на `/kodik/*` по адресу, как у комнат и токена: отдельная корзина.
- **Белый список** (§6a): `/kodik/*` только с токеном Shikimori аккаунта из списка; обмен и
  обновление токена с веб-адресом возврата — только для аккаунтов из списка.
- Разбор страниц и расшифровка ссылок — порт `KodikHtmlParser` и `KodikLinkDecoder` на
  TypeScript, проверенный на тех же фикстурах, что Kotlin-версия (`shared/src/commonTest`).

## 5. Видео

**Обычный путь.** Воркер отдаёт ссылки, браузер играет их сам: hls.js, а в Safari — нативный HLS.
Chromecast уже играет HLS Kodik в браузерном приёмнике, так что CDN Kodik отдаёт CORS для чужой
страницы; это ожидание, которое проверяет проба.

**Проба — первая задача плана, до остального.** Воркер (временный маршрут или `wrangler dev
--remote`) резолвит серию с IP Cloudflare, браузер на Маке играет полученную ссылку: плейлист,
сегменты, перемотка. Итог записывается в спецификацию.

- **Играет** — обычный путь, дальше по плану.
- **Не играет из-за привязки к IP** — воркер проксирует и плейлист, и сегменты
  (`/kodik/media/*`, переписанный `.m3u8`). Это решение пользователя: «только свой плеер». **Риск:**
  условия бесплатного плана Cloudflare запрещают раздачу через Workers преимущественно видео.
  Если проба упирается сюда, работа **останавливается** и выбор — платный план, другой прокси
  или отказ — за пользователем.

**Итог пробы (2026-09-24): играет, прокси для видео не нужен.** Воркер в `wrangler dev
--remote` (сеть Cloudflare) резолвил «Тетрадь смерти», 1 серию; ссылки подписаны до часа вида
`2026092419` и указывают на `sky.solodcdn.com`. С Мака, то есть с другого IP:

- плейлист — `302` на узел `apollo.sky.solodcdn.com`, затем `200`, оба с
  `Access-Control-Allow-Origin: *`; сегменты относительные (`./240.mp4:hls:seg-1-v1-a2.ts`);
- первый сегмент — `200`, `video/MP2T`, `Access-Control-Allow-Origin: *`, настоящий MPEG-TS;
- headless Chrome с hls.js 1.5.20 (`tools/kodik-probe/`): `manifest parsed`, фрагменты 1–7,
  `PLAYING`, перемотка на 600 с — фрагменты 99+, через 10 с `currentTime` = 618, `readyState` 4.

Ссылки Kodik к IP резолвера не привязаны, CDN отдаёт CORS любой странице. Видео идёт из браузера
напрямую в CDN Kodik; `/kodik/media/*` не делается, вопрос о правилах Cloudflare снят.

**Плеер** — свой, на `<video>`:

- Качество: у Kodik нет мастер-плейлиста, качество = отдельный плейлист, смена качества —
  перезагрузка источника с той же позиции (как `AVPlayerItem` на iOS).
- Озвучка: список из `/kodik/translations`, запомненный выбор на тайтл в `localStorage`, порядок
  студий по умолчанию тот же, что в приложениях.
- Автопереход и пропуск эндинга — по тем же правилам и таймингам, что `SkipRules` /
  `EpisodeQueue` на Android; настройки в `localStorage`.
- Клавиатура: пробел — пауза, ←/→ — 10 с, F — полный экран, M — звук, N — следующая серия.
- Порог просмотра (по умолчанию 90 %) отмечает серию на Shikimori.
- Ошибки: «источник не ответил», «нет этой серии в озвучке», «нет сети» — те же тексты, что в
  приложениях, с «Повторить».

## 6. Вход и данные Shikimori

- API Shikimori отвечает браузеру напрямую (`access-control-allow-origin: *`, проверено
  2026-09-24) — клиент ходит в него сам, как `ShikimoriClient`: те же запросы, заголовок
  `User-Agent` не выставляется (браузер не даёт), вместо него — `X-Requested-With: Kaeru`.
- **OAuth**: код авторизации на `https://kaeru.vitaliy.velikodniy.name/auth`, обмен кода и
  обновление токена — через `POST /oauth/token` воркера, который добавляет секрет. Воркер
  разрешает этот адрес возврата наравне с `kaeru://oauth` и OOB.
- **Действие пользователя:** добавить `https://kaeru.vitaliy.velikodniy.name/auth` в адреса
  возврата приложения Kaeru на Shikimori. Без этого вход в браузере невозможен, а без входа веб-
  версия закрыта целиком (§6a).
- Токены хранятся в `localStorage`; выход удаляет их.
- **Без входа нет ничего**, кроме экрана входа: ни каталога, ни плеера, ни совместного просмотра.
  Это следствие белого списка (§6a), и оно сильнее прежнего «гость может смотреть без аккаунта».

## 6a. Белый список

- **Что это.** Список числовых id пользователей Shikimori. Войти в веб-версию и пользоваться ею
  может только аккаунт из списка. Остальные видят экран входа; после входа чужим аккаунтом —
  экран «Доступ закрыт» с его ником, кнопкой «Выйти» и строкой, у кого просить доступ.
- **Где проверяется — в воркере, не в браузере.** Проверка в браузере обходится одной строкой в
  консоли; всё, что стоит защищать, — резолв видео Kodik — живёт в воркере, там и проверка:
  - `POST /oauth/token` **из браузера** — запрос с заголовком `Origin` сайта. Обновление токена
    адреса возврата не несёт, поэтому веб отличается от приложений именно по `Origin`: браузер
    ставит его на каждый запрос к чужому домену сам и подделать его из страницы не может, а
    приложения его не шлют. После обмена кода или обновления воркер спрашивает у Shikimori
    `GET /api/users/whoami` с полученным токеном; id не из списка — ответ `403` с телом
    `{"error":"not_allowed","nickname":"<ник>"}`, и токен клиенту **не отдаётся**.
  - `/kodik/*` требуют `Authorization: Bearer <токен Shikimori>`. Воркер узнаёт владельца через
    `whoami` и запоминает ответ по хэшу токена на 10 минут (в памяти изолята), чтобы не спрашивать
    Shikimori на каждую серию. Нет токена или id не из списка — `401`/`403`.
  - Удаление id из списка действует не позже чем через 10 минут и при следующем обновлении токена.
  - Токен, полученный через приложение (`kaeru://oauth`, без проверки списка), в браузере не
    поможет: `/kodik/*` проверяют владельца токена сами. Каталог Shikimori публичен и так.
- **Где лежит список.** Секрет воркера `WEB_ALLOWED_SHIKIMORI_IDS` — id через запятую. Меняется
  командой `npx wrangler secret put WEB_ALLOWED_SHIKIMORI_IDS` без изменения кода и без выкладки
  сайта. Пустой или отсутствующий список закрывает веб-версию для всех, а не открывает её.
- **Приложения не затронуты.** Запросы с адресами возврата `kaeru://oauth` и OOB идут как раньше,
  без проверки; маршруты `/kodik/*` приложениям не нужны — они резолвят Kodik сами.
- **Совместный просмотр.** Релей комнат не меняется: комната по-прежнему защищена ключом из
  ссылки. Но чтобы войти в комнату из браузера, друг должен быть в белом списке — иначе он видит
  «Доступ закрыт» и кнопки «Открыть в Kaeru» / «Установить». Это ограничивает сценарий «друзья
  без приложения» теми друзьями, чьи id внесены.
- **Что видит закрытый пользователь.** Ник и аватар из `whoami` (это его собственные данные),
  «Kaeru для браузера открыт по приглашению», «Выйти». Никаких данных каталога.

## 7. Совместный просмотр

- Тот же релей, тот же формат кадров и та же семантика, что в `docs/dev/together-protocol.md`:
  AES-128-GCM через WebCrypto, AAD = id комнаты + байт стороны, `hello`/`state`/`play`/`pause`/
  `seek`/`episode`/`chat`/`reaction`/`voice`/`ping`/`pong`/`bye`, эпоха в `hello`, защита от
  повтора, окно возвращения 30 с (хозяин после окна снова ждёт друга — как с 1543413).
- Веб-клиент может быть **и хозяином, и гостем**. Эталон — хозяин; подстраивается только гость:
  `playbackRate` 0,97/1,03 внутри полос, перемотка за их пределами, ожидание загружающегося друга
  до 20 с. Позиция для отчёта — `video.currentTime` в момент отправки.
- Экран приглашения открывается только после входа аккаунтом из белого списка (§6a); до входа —
  экран входа, который помнит ссылку и возвращает к приглашению после входа.
- Экран приглашения — порт `JoinScreen`/`TogetherJoinView`: постер, «кто, какая серия, с какой
  минуты», «Смотреть вместе», «Не сейчас» (без `bye`).
- Голосовые: воспроизведение клипов AAC/MPEG-4 через `<audio>`; запись через `MediaRecorder` только
  при `MediaRecorder.isTypeSupported("audio/mp4")` с кодеком AAC — иначе кнопки нет.
- «Оба открыли ссылку» (`sameSide`) распознаётся и объясняется, как на обеих платформах.

## 8. Интерфейс

- Тёмная тема и палитра Kaeru (фон, поверхность, янтарный акцент), шрифт Manrope, как в
  приложениях.
- Раскладка: на широком экране — боковая панель разделов и полки постеров; на узком (телефон без
  приложения) — нижняя панель и одна колонка. Плеер — во весь экран окна с оверлеем чата и реакций.
- Доступность: вся навигация с клавиатуры, видимый фокус, подписи для экранных чтецов, контраст
  текста на янтаре — тёмный текст (`onAccent`), не белый.

## 9. Аналитика

Firebase Analytics JS в том же проекте `kaeru-fceb3`, свойство `device=web`, события и параметры —
те же, что в `Reporting` на Android и iOS: `screen_view`, `play_start`, `play_error`, `together`.
Crashlytics в браузере нет; необработанные ошибки уходят событием `web_error` с типом ошибки и
её первой строкой, без пользовательских данных. Тумблер «Отправлять статистику» в настройках, по
умолчанию включён — поведение как в приложениях. Отказ от входа (`not_allowed`) — событие
`web_denied` без id и ника.
Никогда не отправляются комнаты, ключи, ники, переписка, токены.

**Действие пользователя:** зарегистрировать в Firebase Web-приложение и прислать его конфиг
(`firebaseConfig`). Конфиг Web-приложения — публичный по устройству, но в репозиторий не
кладётся, как `google-services.json`: сборка читает его из `web/.env.local`; без него аналитика
выключена, остальное работает.

## 10. Проверка

- **Vitest**: кодек совместного просмотра на векторах, общих с Kotlin (зашифрованный кадр и его
  JSON — одинаковые на обеих сторонах); правила синхронизации (полосы, ожидание, окно
  возвращения); разбор страниц Kodik и расшифровка ссылок на фикстурах `shared/src/commonTest`;
  клиент Shikimori на записанных ответах.
- **Воркер**: тесты `infra/relay` дополняются маршрутами `/kodik/*`, CORS, адресом возврата и
  белым списком — id в списке, не в списке, пустой список, отсутствующий токен, кэш `whoami`,
  приложения с `kaeru://oauth` проходят без проверки.
- **Playwright** по собранному сайту: главная, поиск, карточка, плеер на заглушке HLS,
  экран приглашения; прогон в Chromium и WebKit.
- **Пробник** `tools/together-probe` против релея — без изменений.
- **Вручную**: комната браузер ↔ Android и браузер ↔ iPad в обе стороны; просмотр серии до
  отметки на Shikimori.

## 11. Порядок работ

1. Проба видео (§5). Результат решает судьбу прокси сегментов.
2. Воркер: `/kodik/*`, CORS, адрес возврата OAuth, белый список.
3. `web/`: каркас, тема, маршруты, клиент Shikimori, вход.
4. Главная, поиск, карточка, «Мой список».
5. Плеер.
6. Совместный просмотр.
7. Аналитика, публикация на `gh-pages`, ручной прогон с телефонами.

## 12. Что делает пользователь

1. Добавляет адрес возврата `https://kaeru.vitaliy.velikodniy.name/auth` в приложении Shikimori.
1a. Присылает id Shikimori, которые пускать (свой и друзей); список ставится секретом воркера.
2. Регистрирует Web-приложение в Firebase и присылает конфиг.
3. Если проба упрётся в правила Cloudflare — решает, как быть (§5).
