# Kaeru relay

Cloudflare Worker и Durable Object, которые пересылают кадры совместного просмотра между двумя
телефонами. Нужны там, где прямое соединение невозможно: NAT, CGCNAT, разные сети.

Релей ничего не понимает в том, что пересылает. Телефоны шифруют каждый кадр AES-GCM ключом, который
живёт только во фрагменте ссылки-приглашения и до сервера не доходит. Релей видит идентификатор
комнаты, два IP, тайминги и объём байтов — и всё.

## Протокол

| Маршрут | Ответ |
| --- | --- |
| `GET /health` | `200 ok` |
| `GET /w/<roomId>` | апгрейд до WebSocket в Durable Object комнаты |

`roomId` лежит в пути и должен подходить под `^[A-Za-z0-9_-]{8,16}$`. Всё, что не подходит, получает
`400`. Запрос без заголовка `Upgrade: websocket` получает `426`, любой метод кроме `GET` — `405`,
чужой путь — `404`.

Комната — одна на `roomId` (`idFromName`), в ней ровно два места. Отдельного кадра «join» нет:
комната определяется путём.

**От телефона к серверу** идут только бинарные кадры не больше 64 КиБ. Кадр пересылается второму
участнику дословно и никогда не возвращается отправителю. Если второго нет, кадр молча теряется.
Текстовые кадры от телефона игнорируются.

**От сервера к телефону** идут только текстовые кадры — это управляющие сообщения в JSON. Такое
сообщение одно:

```json
{"type":"peer-left"}
```

Оно приходит оставшемуся, когда сокет второго закрылся или оборвался. Поэтому клиенту достаточно
правила «бинарный кадр — данные, текстовый — управление».

Коды закрытия — это HTTP-статус плюс 4000, обычный способ положить статус в приватный диапазон
WebSocket:

| Код | Когда |
| --- | --- |
| `4408` | комната шесть часов не видела ни одного кадра, будильник её закрыл |
| `4409` | в комнате уже двое; третьему сокет открывается и тут же закрывается с `room full` |
| `4413` | отправитель прислал кадр больше 64 КиБ; закрывается только он, второй получает `peer-left` |

Третий участник получает именно код закрытия, а не отказ в рукопожатии: так OkHttp на Android
приходит в `onClosing(4409, "room full")` и может показать честное «комната занята», а не общую
ошибку сети.

## Как это устроено

`src/index.ts` — весь релей: Worker с маршрутами и класс `RoomDO`.

Сокеты принимаются через WebSocket Hibernation API (`state.acceptWebSocket`, `webSocketMessage`,
`webSocketClose`, `webSocketError`), поэтому комната, в которой двое молчат, не стоит ничего:
рантайм выгружает объект из памяти и будит его на каждый кадр. Из-за этого в памяти между кадрами
не хранится ничего важного — список участников берётся из `getWebSockets()`, а метка комнаты для
логов из вложения сокета.

Кадры нигде не сохраняются. В лог идут только первые четыре символа `roomId` и вид события:
`join`, `refused`, `close`, `error`, `oversize`, `idle-close`. Полезной нагрузки в логах нет.

Будильник простоя переписывается не чаще раза в пять минут, иначе на каждый кадр приходилась бы
запись в хранилище — а кадр состояния летит раз в секунду. Поэтому комната закрывается не ровно
через шесть часов после последнего кадра, а между шестью часами и шестью часами пятью минутами.
Порог живёт не только в памяти: свежий объект после пробуждения один раз читает `getAlarm()`, иначе
после каждого пробуждения счёт начинался бы заново и запись всё-таки приходилась бы на каждый кадр.

Обработчик будильника ничего не удаляет из хранилища. Сработавший будильник рантайм снимает сам, а
больше комната ничего не пишет, так что всё, что лежит в хранилище к этому моменту, принадлежит
подключению, которое успело прийти в том же ходу.

## Разработка

```sh
npm install        # один раз
npm test           # 26 тестов в настоящем workerd через Miniflare
npm run typecheck  # tsc --noEmit
npm run build      # wrangler deploy --dry-run --outdir dist, проверка сборки
npm run dev        # локальный сервер на http://localhost:8787
```

Тесты идут через `vitest` и `@cloudflare/vitest-pool-workers`, то есть внутри того же рантайма
`workerd`, который работает в проде, с биндингами из `wrangler.toml`. Дата совместимости в
`wrangler.toml` закреплена на `2026-08-22` — это самая свежая дата, которую принимает `workerd`,
вшитый в пул тестов.

Из `src/index.ts` можно экспортировать только обработчик и класс Durable Object. Воркер, у которого
в модуле лежит экспорт-значение, `workerd` не запускает вовсе. `wrangler deploy --dry-run` этого не
ловит — он только собирает бандл, — а `npm run dev` и настоящая выкладка ловят. Поэтому после правок
в экспортах стоит поднять `npm run dev` и проверить хотя бы `curl http://127.0.0.1:8787/health`.

## Выкладка

Выкладка требует аккаунта Cloudflare и интерактивного входа, поэтому её делает человек.

```sh
cd infra/relay
npm install
npx wrangler login      # откроет браузер
npx wrangler deploy
```

`wrangler deploy` напечатает адрес вида `https://kaeru-relay.<account>.workers.dev`. Дальше:

1. Проверить, что живо: `curl https://kaeru-relay.<account>.workers.dev/health` → `ok`.
2. Положить адрес в `local.properties` в корне репозитория, со схемой `wss`, без слеша на конце:

   ```properties
   TOGETHER_RELAY_URL=wss://kaeru-relay.<account>.workers.dev
   ```

3. Пересобрать приложение. Клиент читает адрес из `BuildConfig.TOGETHER_RELAY_URL` и дописывает
   `/w/<roomId>` сам. Пустое значение означает «сервер не настроен» — совместный просмотр через
   релей выключен, LAN-транспорт работает по-прежнему.

Логи в реальном времени:

```sh
npx wrangler tail
```

Бесплатного тарифа хватает с запасом: 100 000 запросов в сутки, входящие сообщения WebSocket
тарифицируются 20 к 1, исходящие и пинги бесплатны, а спящая комната не начисляет время.

### Свой домен, когда понадобится

Пока используется адрес `*.workers.dev`. Чтобы переехать на `relay.kaeru.vitaliy.velikodniy.name`,
нужно завести зону `vitaliy.velikodniy.name` в Cloudflare, раскомментировать блок `[[routes]]` в
`wrangler.toml`, выложить заново и поменять `TOGETHER_RELAY_URL`.
